What I do

  • Carry things through on my own

    I handle design, implementation, release and operation by myself. Everything below has shipped or is running in production (Sirube, Sudare and Warframe State Graph as releases, loopfinder on the VS Code Marketplace, grounding-check on GitHub, the Focal Length Checker, the CMS and Ruv live on Cloudflare).

  • Check against the real thing, not assumptions

    I don't stop at "it should work"; I run it and look at the difference. loopfinder's tests check both the with-hook and without-hook sides, and after each deploy of the CMS I actually send requests that should be rejected.

  • Design within constraints

    I shape things assuming budget, APIs or permissions will fall short. Ruv splits its processing into stages to fit the free plan's 10 ms CPU limit, and Warframe State Graph uses one-tap input instead of auto-sync because there's no official inventory API.

  • Make it understandable to others

    I write up what I build so other people can follow it. The CMS's defenses became a book on Zenn, and Ruv's memory design became articles (both in Japanese).

    Things I've built

    Migration and maintenance

    A record of keeping a personal site (Astro + Cloudflare Workers, home of the CMS above) upgraded and fixed while it stays live in production.

    • Major framework migrations (Astro 5 → 6 → 7)

      Going from 5 to 6, I hit the fact that on Cloudflare Pages a page can't call its own API while rendering (1042 Loopback), so I dropped Pages and moved the whole setup to Workers. Data now comes from a layer that reads R2 and KV directly instead of going over HTTP. Going from 6 to 7, the build stopped with an error saying it might be a bug in Astro. I nearly blamed open upstream issues, but dug back in and found the cause in my own package.json: an override pinning Vite to an old version. I also fixed a regression that showed up after release, where CSS minification dropped the blur (backdrop-filter).

    • Measure what's slow, then fix it

      One page read KV 14 times in sequence, so with a cold edge cache it took about 3.7 seconds to respond. I batched the reads in parallel and re-measured with a cold cache: 3.75 s → 0.34 s (about 11× faster). The admin screens fetched every record one by one (N+1); they now read from the index that already exists. The API was also returning no-store, leaving the cache hit rate at 0.9%; I tracked that down and removed it.

    • Audit and close holes in my own production

      I went through the public APIs and the upload path and closed what I found, such as an endpoint that accepted writes without logging in, and one that served files with whatever Content-Type the upload declared. When a storage setting left the original images open to anyone, I shut off public access first and fixed the leaks in the delivery path afterwards. Twice, a defense I had already fixed quietly came undone through later changes, so I wrote tests that send requests which should be rejected, and CI runs them on every deploy.

    • Keep dependencies moving

      Updates had fallen behind because they were left to manual work, so I set up Dependabot, then fixed its PRs all failing in CI for lack of permissions and piling up. A major update (zod v4) broke the admin screen's error display and sat in production for three months; I traced and fixed it once I noticed it there. I handled the removal of Node 20 from GitHub Actions ahead of the deadline, and each week I read the dependency diffs and Cloudflare's changelog and file tickets for what applies.
